# Работа с сайтом семейного психолога

Применяй этот процесс для задач в репозитории `family-therapy-site`. Сначала сохрани существующую работу пользователя, затем вноси минимальные проверяемые изменения. Не заменяй чтение текущего кода предположениями из документации.

## 1. Определи границы проекта

Корень репозитория содержит `index.html`, `about.html`, `SPEC.md` и каталог `server`.

- Если текущий каталог сам является корнем сайта, работай в нём.
- Если текущий каталог — `lending-family-therapy`, сайт находится во вложенном каталоге `family-therapy-site`.
- Не изменяй соседние `backups`, `tmp`, внешние `.claude` и другие проекты.
- Не включай локальные DOCX, скриншоты и корневой `SKILL.md` в коммиты: это рабочие материалы, а не исходный код сайта.
- Не удаляй и не переименовывай файлы без явного подтверждения пользователя.

GitHub-репозиторий: `https://github.com/galikura/family-therapy-site`, основная ветка — `main`.

## 2. Изучи актуальное состояние

Перед правками выполни:

```bash
git status --short --branch
git diff
```

Не перезаписывай незакоммиченные изменения пользователя. Прочитай целевой файл и связанные с ним файлы целиком или нужными фрагментами.

Источники сведений используй в таком порядке:

1. Текущий HTML, CSS и JavaScript — фактическое поведение проекта.
2. `README.md` — запуск, настройка, публикация и текущие ограничения.
3. `server/README.md` — настройка Telegram и Cloudflare Worker.
4. `SPEC.md` — исходные требования и дизайн-система; при расхождении с кодом не считай спецификацию описанием текущего состояния.
5. `КАК-РЕДАКТИРОВАТЬ.md` — инструкция по редактированию контента; проверяй её актуальность перед изменением связанных инструкций.

## 3. Помни структуру и зоны ответственности

```text
index.html                 Главная страница и все основные секции
about.html                 Страница «Обо мне»
css/style.css              Общие стили, переменные и адаптивность
js/script.js               Год, анимации, валидация и отправка формы
img/photo.jpg              Фотография на обеих страницах
server/worker.js           POST-обработчик и отправка в Telegram
server/README.md           Настройка Wrangler, секретов и CORS
README.md                  Главная документация репозитория
SPEC.md                    Исходная спецификация
```

Основные якоря главной страницы: `#hero`, `#benefits`, `#trust`, `#services`, `#form`, `#contacts`.

Вноси изменения в соответствующий слой:

- тексты, контакты, цены, мета-теги и разметка — в HTML;
- оформление, точки перелома и анимации — в `css/style.css`;
- поведение формы и появление секций — в `js/script.js`;
- серверная валидация, CORS и Telegram API — в `server/worker.js`;
- команды и описание поведения — в соответствующем README.

Не добавляй React, Vue, Tailwind, jQuery, сборщики, препроцессоры и npm-зависимости фронтенда без отдельного запроса. Проект должен открываться как статический сайт без сборки.

## 4. Соблюдай содержательные и технические правила

- Пиши интерфейс и документацию на русском, спокойно и ясно, без агрессивного маркетинга.
- Не выдумывай опыт, образование, методы, цены, отзывы, кейсы и результаты. Неизвестные факты обозначай `[УКАЗАТЬ]` и спрашивай пользователя.
- Демонстрационные отзывы не представляй реальными; для публикации нужны реальные отзывы с согласия клиентов либо удаление блока.
- Сохраняй семантическую разметку, один `h1` на странице, подписи полей, клавиатурный фокус и `aria-live` у статуса формы.
- Сохраняй поддержку `prefers-reduced-motion` и мобильную вёрстку.
- Не используй `alert()` для формы и не снимай блокировку кнопки до завершения запроса.
- Не переноси токен Telegram в браузерный код и не отключай серверную валидацию.
- Не делай несвязанный рефакторинг или редизайн вместе с точечной задачей.
- Таблицы в документации создавай только по явному запросу пользователя.

## 5. Запускай статический сайт

Для быстрой проверки можно открыть `index.html` напрямую в браузере.

Для локального HTTP-сервера из корня репозитория используй доступный вариант:

```bash
py -m http.server 8000
```

или:

```bash
python3 -m http.server 8000
```

Открой `http://localhost:8000`. Не устанавливай дополнительные пакеты ради простого статического запуска.

Если порт занят, сначала проверь причину и выбери свободный порт, не завершая чужой процесс без подтверждения.

## 6. Запускай Cloudflare Worker

Для Worker нужны Node.js, Wrangler и конфигурация `server/wrangler.toml`. Сначала проверь их наличие и следуй `server/README.md`.

```bash
cd server
wrangler dev
```

По умолчанию локальный адрес — `http://localhost:8787`.

- Локальные секреты храни в `.dev.vars`; этот файл должен оставаться игнорируемым.
- Реальные секреты Cloudflare задавай через `wrangler secret put`, а не через файлы проекта.
- Для браузерной формы локальный адрес задаётся в `FORM_ENDPOINT` в `js/script.js`.
- CORS настраивается через `ALLOWED_ORIGIN` в `server/worker.js`.
- `ALLOWED_ORIGIN = "*"` допустим только временно для локальной проверки; перед production верни точный домен.
- Не выводи значения секретов в терминал, документацию или итоговый отчёт.

Если нет учётных данных или настройки Cloudflare, проверь только доступную статическую часть и прямо укажи, что отправка формы не тестировалась.

## 7. Обновляй README при изменениях

Обновляй `README.md`, если изменились:

- структура файлов или назначение каталогов;
- команды запуска, проверки или публикации;
- требования и зависимости;
- переменные, секреты, endpoint или правила CORS;
- поведение формы и Worker;
- ограничения, известные заглушки или чеклист запуска.

При серверных изменениях синхронизируй также `server/README.md`. При изменении процесса редактирования проверь `КАК-РЕДАКТИРОВАТЬ.md`.

README должен описывать реальное состояние, а не планируемые возможности. Не утверждай, что форма работает, если `FORM_ENDPOINT` остаётся заглушкой. Не добавляй несуществующие тесты, лицензии, URL, функции или учётные данные. Сохраняй существующую структуру документа и относительные ссылки.

Изменение только текстов или фотографии обычно не требует правки README.

## 8. Проверяй ошибки

После изменений выполни доступные базовые проверки из корня:

```bash
node --check js/script.js
node --check server/worker.js
git diff --check
```

Затем проверь затронутые сценарии:

- открываются `index.html` и `about.html`;
- локальные CSS, JavaScript и изображения загружаются без ошибок 404;
- навигация и якоря ведут в существующие секции;
- нет ошибок в консоли браузера;
- мобильная и десктопная вёрстки не ломаются;
- клавиатурный фокус видим, а уменьшение движения работает;
- форма показывает ошибки обязательных полей и согласия;
- кнопка блокируется во время отправки;
- отдельно проверены успешный ответ, HTTP-ошибка и сбой сети;
- Worker принимает корректный JSON и отклоняет неправильный метод, пустые или слишком длинные поля;
- production CORS разрешает только домен сайта.

Не выдумывай результаты браузерных или сетевых проверок. Если инструмент для проверки недоступен, сообщи, что именно осталось непроверенным.

## 9. Готовь проект к публикации

Перед коммитом или push:

1. Проверь `git status`, `git diff` и состав staged-файлов.
2. Убедись, что в коммит не попали `.dev.vars`, DOCX, локальные скриншоты, резервные копии, журналы и корневой `SKILL.md`.
3. Проверь рабочее дерево и будущий коммит на токены, пароли и приватные ключи. Не печатай найденные секреты целиком.
4. Обнови документацию и выполни проверки из раздела 8.
5. Перечисли оставшиеся заглушки: телефон, `FORM_ENDPOINT`, `ALLOWED_ORIGIN`, демонстрационные отзывы и непроверенные факты.
6. Убедись, что статический хостинг публикует корень репозитория без команды сборки, а Worker разворачивается отдельно.

Commit и push выполняй только по явному запросу пользователя. Деплой сайта, Worker или изменение публичного домена выполняй только после отдельного разрешения. Создание коммита не означает разрешение на push, а push не означает разрешение на деплой.

После разрешённой публикации проверь удалённую ветку и доступность изменённых файлов. Для сайта дополнительно проверь обе страницы и форму на реальном домене, если настроены Worker и секреты.

## 10. Сообщай результат кратко

В итоге укажи:

- что изменено;
- изменённые файлы одной строкой или коротким списком;
- какие проверки действительно выполнены и их результат;
- что не проверено и какие заглушки остались;
- был ли создан коммит, выполнен ли push или деплой.

Не пересказывай весь процесс и не сообщай о публикации, если изменения остались только локально.
